# 0001 规则优先的提问诊断，LLM 只做可选润色

- 状态：已采纳
- 日期：2026-11-05

## 背景

用户的问题是“对话时提问得不到想要的答案”。本机已有 `prompt-optimizer` 技能，它擅长把一句话改写成结构化提示词；但那是“写提示词”，不是“在对话中把需求问清楚”。

需要的是一个本地、可离线、可测试、结果稳定的工具：先指出问题缺了什么，再给出追问清单和可粘贴的改写稿；答非所问时能复盘出下一轮追问。

## 决定

1. **规则优先**：用 7 个槽位（目标、背景、约束、期望输出、验收标准、受众/用途、示例）和 6 个反模式做检测。分数只用于趋势比较，不宣称准确率。
2. **LLM 可选**：只支持 OpenAI 兼容的 chat completions 端点，默认关闭，每次显式开启；失败时降级为规则结果，规则结果永远保留。
3. **历史只存元数据**：时间、模式、分数、缺失/薄弱槽位、反模式、字符数、是否用 LLM；不存问题原文，也不存 AI 回答。
4. **只用 Python 标准库**：CLI 与网页共用同一套纯函数；网页用 `http.server`，无需构建步骤。
5. **依赖方向硬约束**：`tools/check_layers.py` 用 AST 检查分层和第三方依赖，违反即 lint 失败。

## 后果

- **代价**：规则对中文的覆盖有限，措辞或领域变化会误判；复杂语义（前提是否成立、回答是否真的跑题）无法自动判断，复盘模式需要用户自己选“哪里不对”。规则表需要用真实案例持续校准。
- **收益**：离线可用、结果稳定、测试成本低、无数据外发；LLM 只是加分项，不是单点依赖；CLI 和网页不会各写一套逻辑。
- **什么时候重新考虑**：当真实案例显示规则覆盖率长期不可接受，或需要跨会话的语义记忆时，再引入检索或模型判断；届时保留规则结果作为基线，不要直接替换。
